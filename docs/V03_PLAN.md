# LureSense 第三版开发计划与检查点

日期：2026-09-26。范围：淡水大口黑鲈；不判断现场有鱼，不输出中鱼率。

## 已观察到的问题

1. 用户实际运行固定RAG：模糊问题“我在淡水边，应该先看哪里？”检索为空，未调用模型。
2. 用户实际运行水温问题：引用存在，但“需要精确水温数据”等结论超出了展示卡片直接支持的范围。
3. 模型追问“如何准确测量……”更像话题推荐，不是收集用户条件。
4. 第二版逐题独立，没有会话事实状态；引用检查只验证编号。

## 第一步：本次可运行交付

新增clarification.py、agent_cli.py、tests/test_clarification.py。本包是第二版的增量包，依赖仓库原有retriever.py与data/；不是独立完整项目。

这是规则控制的引导式澄清，不是LLM自主选择工具的完整Agent。不会调用模型，不需要API Key。只展示候选证据，不生成已经验证适用性的现场建议。

初始问题暂按原文保留，不自动抽取或改写。编号修改只影响后续结构化选择：如果初始问题写了“湖泊”，后来发现应为“河流”，请用/new重开，避免原文残留矛盾。原检索器不能可靠理解否定句，不能把候选结果视为条件过滤结果。

## 第二步：状态接入生成（下一次开发）

先保存本次结果并提交。下一次只实现：任务路由、避免重复问已知条件、把原问题与结构化状态分别传给生成器，以及用户纠正后的事实优先级。不要简单把全部聊天历史拼成检索关键词。

初始约束：最多2个自动追问，每个会话最多3次模型请求（含条件提取/生成/修复），API失败也占调用预算，不静默重试。预算耗尽后返回已知信息和不足。

需保留第二版原入口，新的Agent单独入口；生成前展示已知/未知条件，用户自述不得标为实测。

验收：相同补充条件下，自动流程与手工完整问题的检索输入可比较；返回答案保留未知与地区限制；用户改口后不再使用旧条件。简单食性问题不触发水域问卷。

## 第三步：证据与对照实验

先用10个开发场景查错，类别包括模糊输入、信息完整、不知道、未观察到、改口、温度来源、范围不适用、接口故障。场景的“正确”标签是证据支持与流程行为，不是鱼情真值。

至少比较三组：B第二版固定RAG（原始问题）；B+同样补充信息（手动给出完整条件）；C第三版澄清流程。这样可区分“信息更多”与“流程设计”的作用。对所有组使用同一知识版本和模型配置。

主要记录：无依据主张率、可回答题有效回答率、条件处理正确率、追问次数、模型调用数、token与耗时。拒答、解析失败、接口失败均计入运行总数并单列，不能删去。

新增测试集应与开发集按基础场景分开，不能把同义改写分到两边。此次8项新增测试是软件测试，不是研究评估数据。

## 暂不加入

图片、偏光眼镜、地图、实时鱼情预测、多Agent、向量数据库迁移、模型训练。先证明这一项澄清机制在明确指标下有用。
