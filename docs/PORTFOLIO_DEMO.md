# 面向求职的项目讲解与下一阶段

## 项目定位

LureSense 是面向淡水大口黑鲈知识咨询的个人 Agent 工程项目，使用受控工作流完成问题分类、条件澄清、知识检索、模型回答、引用校验与运行记录导出。当前检索是关键词/概念匹配，澄清是有限状态规则；不是通用自主规划系统。

## 三分钟演示顺序

1. 30 秒解释问题：模糊现场描述容易导致模型补造条件，需要显式记录未知信息并限制结论。
2. 60 秒展示“我在淡水边”的两轮澄清和证据面板；解释事实、推断与用户自述的区别。
3. 45 秒修改条件，让检索和回答重算，指出历史记录保留原版本。
4. 30 秒演示两项未知时停止回答，不为演示强行生成结论。
5. 15 秒导出 JSON，说明如何交给人工评估。

## 你需要自己能解释的实现

- 为什么先澄清再检索，哪些知识问题无需澄清。
- 为什么 UNKNOWN 与尚未提供是不同状态。
- 修改条件如何防止旧关键词污染下一次检索。
- 引用编号合法、摘录真实存在、结论被支持，是三个不同层次。
- 请求失败为何仍占用预算，预算为什么只能约束单次会话。
- 为什么测试替身验证的是程序契约，不证明真实模型质量。
- 为什么轻量标准库 Web 服务适合本地个人演示，未来哪些需求才值得迁移框架。

## 简历能写什么

可如实描述：实现面向淡水路亚知识的受控 RAG 工作流，支持有限澄清、条件修正、引用摘录校验与可追溯运行记录；开发本地 Web 演示并建立状态流转、模型异常与接口回归测试。

不要写未经测量的准确率提升、中鱼率提升、工业级部署、多智能体自主决策、实时视觉识鱼。项目代码应由你运行、理解并持续修改；面试时能解释设计取舍比堆功能更重要。

## 下一阶段应优先补实验

页面完成后，优先建立一套固定评估案例并比较已有版本，不急于增加新框架。建议先手工撰写 30 个情景，覆盖：清晰知识问题、模糊现场问题、未知条件、条件修正、范围外鱼种、无证据问题。固定模型、知识库和案例，记录版本、失败次数、token、耗时。

同一案例比较“直接检索回答”与“澄清后检索回答”，人工标注条件是否正确、结论是否获支持、拒答是否适当。开发案例和最终留出案例分开；不要把多轮响应当作独立情景扩大样本数。样本量小则报告计数、分母和失败案例，暂不声称统计显著。

当前这轮实现的是可展示的工程闭环；上述对比实验尚未执行，不能当作已完成成果。
